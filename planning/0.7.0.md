# SleepManager 0.7.0

Development status and release-validation notes for the 0.7 development cycle.

0.7.0 continues the large reliability/architecture work started on the former 0.6.2 branch and adds enough behavior fixes, diagnostics and protocol hardening to justify a minor release.

## Release identity

- Main development version: `0.7.0-dev1`
- Main versionCode: `548`
- Helper development version: `1.1.2`
- Helper versionCode: `1113`
- Development branch: `dev/0.7.0`
- Public stable remains `0.6.1` until the full validation gate is accepted.
- Public release must reuse the permanent signing certificate and preserve in-place upgrade compatibility.

### Physical Thor rollback rule

The physical AYN Thor must be returned to **stable 0.6.1** after the 0.7 physical test session.

Rollback rule for 0.7 physical testing:

- The previously prepared `0.6.1 / versionCode 547` rollback was valid for the older 546 candidate only.
- It is **not sufficient** to roll back from a 0.7 candidate whose versionCode is 548 or higher without using Android downgrade flags.
- Before each physical 0.7 test session, build the exact public `v0.6.1` source with a rollback versionCode **higher than the candidate being installed**.
- The Thor test workflow now does this automatically for Main and also prepares a stable Helper 1.1.1 rollback when Helper 1.1.2 is tested.
- Keep the same permanent release signer.
- Install in place with `adb install -r`.
- Never uninstall SleepManager.
- Never clear app data.

Example: candidate Main 548 -> stable 0.6.1 rollback code 549. Any later candidate/final installed after that rollback must then use a versionCode greater than 549.

The same monotonic rule applies to the Helper if its rollback APK is actually installed.

# 1. Reliability fixes

## 1.1 Closed-lid false wake must preserve one sleep transaction

Physical testing exposed this sequence:

`sleep -> false wake while lid closed -> forced re-sleep -> real wake`

The second `SCREEN_OFF` could previously re-enter sleep recovery and lose ownership created by the original sleep. The final real wake could then have nothing left to restore.

### Required invariant

A suppressed closed-lid false wake is **not a new sleep/wake transaction**.

The forced re-sleep must preserve every state/restore token created by the original sleep until a real wake occurs.

Ownerships that must survive:

- Helper Wi-Fi
- Helper Bluetooth
- Syncthing-Fork
- BasicSync
- Tailscale
- JamesDSP
- Battery Saver
- Charging Separation
- future state-aware connectors stored in `SleepCycleStore`

### Implementation status

- [x] Add one-shot runtime state for the `SCREEN_OFF` generated by a suppressed closed-lid false wake.
- [x] Skip duplicate sleep recovery on that one-shot re-sleep.
- [x] Preserve the original `SleepCycleStore` transaction.
- [x] Keep the real wake responsible for restore.
- [x] Add focused `SleepWakePolicy` coverage.
- [x] Add focused `SleepCycleRuntimeState` coverage.
- [x] Record false-wake diagnostics.
- [x] Add an integration regression proving transaction/ownership preservation across:
      sleep -> managed ownership recorded -> false wake -> re-sleep -> real wake ->
      Helper restore + connector ownership completion.
      (`FalseWakeTransactionRegressionTest`; real external-app side effects remain in E2E/Thor validation.)
- [ ] Confirm no connector is briefly restored during the suppressed false wake.
- [ ] Confirm Cocoon audio/background behavior is not resumed during the false wake.
- [ ] Re-test physically on Thor.

## 1.2 Main ↔ Helper protocol hardening

Goal: a delayed or duplicate Helper response from an older sleep cycle must not mutate the current transaction.

### Implemented contract

- [x] New Helper responses echo `cycleId`.
- [x] Main accepts a matching correlated result.
- [x] Main rejects a mismatched/stale correlated result.
- [x] Main temporarily accepts a response without `cycleId` as a legacy Helper 1.1.1 response.
- [x] Helper detects explicit sleep/restore cycle mismatches.
- [x] Add `CYCLE_MISMATCH`.
- [x] Expose the cycle-id contract through shared `HelperProtocol`.
- [x] Record stale/mismatched results in diagnostics.
- [x] Add policy/contract tests.

### Remaining validation

- [x] Add receiver/instrumentation coverage for delayed result from old cycle.
- [x] Add duplicate result coverage.
- [x] Add mismatched sleep request coverage.
- [x] Add mismatched restore request coverage.
- [x] Validate Main 0.7 + Helper 1.1.1 first.
      Real Helper 1.1.1 results without `cycleId` are accepted by Main 0.7.
- [x] Upgrade Helper in place to 1.1.2 and repeat.
      Real Helper 1.1.2 sleep/wake results echo the matching `cycleId` and complete the Main 0.7 transaction.
- [x] Verify stable Main 0.6.1 remains compatible with Helper 1.1.2 before deciding whether Helper also needs rollback after the Thor test.
      Emulator matrix passed with an in-place Main downgrade to 0.6.1 while keeping Helper 1.1.2; protocol compatibility therefore does not require a Helper rollback, though the 1.1.1 rollback APK remains a physical-test fallback.
      Validated on CI at commit `697828eb10fe1f58db4852c87e99a732554e4894`.

# 2. Battery Saver + external power

Physical Thor testing showed that the firmware can refuse Battery Saver while the device is externally powered, including Charging Separation scenarios.

The correct condition is **external power connected**, not Android's textual Charging/Not Charging state.

## Required behavior

- [x] Do not try to enable Battery Saver at initial sleep while external power is connected.
- [x] Keep the user's SleepManager Battery Saver preference enabled.
- [x] Do not take Battery Saver ownership merely because the action was skipped.
- [x] Persist that Battery Saver is deferred for this sleep transaction.
- [x] Listen for `ACTION_POWER_CONNECTED`.
- [x] Listen for `ACTION_POWER_DISCONNECTED`.
- [x] If external power is removed while still effectively sleeping and the action was deferred, enable Battery Saver then.
- [x] If power returns while still sleeping and SleepManager owns Battery Saver, restore the previous state immediately.
- [x] Re-arm the deferred state when appropriate after replug.
- [x] Recover deferred state after service restart.
- [x] Clear deferred state on real wake/disable.
- [x] Add focused policy tests.

## Remaining validation

- [ ] Sleep while plugged: Battery Saver skipped cleanly, no failed privileged write.
- [ ] Unplug while still asleep: Battery Saver becomes ON.
- [ ] Replug while still asleep: previous state restored.
- [ ] Unplug again while still asleep: Battery Saver becomes ON again.
- [ ] Real wake: final state exactly matches the state before the sleep transaction.
- [ ] Battery Saver already ON before sleep: never take ownership or turn it OFF.
- [ ] Management option OFF: power events do nothing.
- [ ] Physical Thor test with Charging Separation enabled.

# 3. Battery capacity sanity fallback — public issue #29

Reporter pattern on AYN Thor Max Batch 3:

- Android battery percent: 80%
- raw `charge_full`: ~8,336,000 µAh
- raw `charge_full_design`: ~5,938,000 µAh
- raw `charge_counter`: ~6,674,635 µAh
- `charge_counter / charge_full` is almost exactly 80%

The bad ~8Ah value is therefore coming from the device/fuel-gauge data rather than being invented by SleepManager.

## Policy

- [x] Introduce dedicated `BatteryCapacityPolicy`.
- [x] Preserve raw values in diagnostics.
- [x] Treat a learned full value as suspect when:
      `charge_full > charge_full_design * 1.25`.
- [x] Preserve plausible learned capacity, including a worn battery where learned full is below design.
- [x] Fall back to `charge_full_design` when learned full is implausibly high.
- [x] If the raw counter is also inconsistent with the selected capacity, derive displayed current charge from:
      `percent × selected full capacity`.
- [x] Expose selected capacity source.
- [x] Expose current-charge source.
- [x] Expose whether learned full was considered suspect.
- [x] Use sanitized values for displayed stats and sleep-stat precision.
- [x] Add tests for normal, worn, high learned full, bad counter, missing full values and rounding.

## Remaining validation

- [ ] Verify the reporter pattern produces approximately 4,750 / 5,938 mAh at 80%.
- [ ] Verify a normal Thor still uses its plausible learned full capacity.
- [ ] Verify 80% charge-limit behavior does not create a false fallback on normal hardware.
- [ ] Review the 1.25 threshold against more devices before treating it as permanent.
- [ ] Confirm diagnostics always expose raw values even while UI uses fallback values.

# 4. Clamshell / Force SELinux — public issue #30

Issue #30 reports that enabling Force SELinux on AYN Thor makes the clamshell section disappear because SleepManager can no longer read the expected lid input path.

## UX already added

- [x] Detect an expected Thor device even when the lid sensor is unreadable.
- [x] Do not silently hide the entire problem.
- [x] Show a concise `Lid sensor unavailable` explanation.
- [x] Explain that Force SELinux can block the required input-device access.
- [x] Keep normal non-Thor devices unchanged.

## Functional investigation still required

The warning is not considered a complete fix for issue #30.

- [ ] Determine whether Thor exposes a second SELinux-safe lid-state source.
- [ ] Check whether standard Android framework/display/power APIs expose usable lid state on this firmware.
- [ ] Check whether a system setting, switch state, uevent, input-manager path or vendor service is available without root/Shizuku/ADB.
- [ ] If a safe fallback exists, introduce it behind `LidMonitor` rather than special-casing UI/service code.
- [ ] If no normal-app path exists, keep graceful explanation and document the firmware limitation.
- [ ] Diagnostics should report:
  - expected clamshell capability
  - detected sensor name
  - detection method
  - event/input path when available
  - current lid state when readable
  - reason/capability failure when unreadable
- [ ] Physical tests with Force SELinux OFF and ON.

Do not add a root, Shizuku or ADB requirement just to work around this firmware behavior.

# 7. Architecture / code-review backlog for 0.7

The 0.6.2 refactor significantly reduced structural debt. 0.7 should avoid undoing that work.

## SleepManagerService

- [ ] Re-audit service size after the new 0.7 fixes.
- [ ] Move any newly-added pure decisions out of the service into Policy classes.
- [ ] Keep Stores responsible for durable ownership only.
- [ ] Keep Android/binder/system writes in Controllers.
- [ ] Review every async callback for stale-generation/cycle handling.
- [ ] Review every Handler runnable for cancellation on real wake, disable and destroy.
- [ ] Review process-death recovery for every persisted ownership state.
- [ ] Ensure no main-thread network or slow ContentProvider work.

## Transaction model

- [ ] Define one invariant for a sleep transaction from first real screen-off until real wake.
- [ ] Ensure false wakes cannot create a new transaction.
- [ ] Ensure connector restore tokens cannot be cleared before confirmed restoration.
- [ ] Ensure stale asynchronous callbacks cannot complete a newer cycle.
- [ ] Ensure user disabling SleepManager performs bounded restoration before service stop.
- [ ] Add focused tests around transaction completion and partial restore failure.

## Connector architecture

Future integrations must use the same ownership model:

1. detect/query initial state
2. change state only when necessary
3. persist a restore token/ownership
4. verify completion when the API supports it
5. restore only what SleepManager changed
6. remain idempotent across duplicate broadcasts/process restarts

- [ ] Keep integration-specific behavior in connector/controller classes.
- [ ] Avoid direct package-private implementation hacks in third-party apps.
- [ ] Prefer official Intent/ContentProvider APIs.
- [ ] Make API version/capability detection explicit.
- [ ] Handle unavailable/unknown state safely rather than guessing.

## UI / ViewModel

- [ ] Continue removing business decisions from Compose.
- [ ] Keep `SleepManagerUiState` as the UI-facing state model.
- [ ] Re-check that periodic refresh cannot flash/null out async state.
- [ ] Keep compact/landscape/responsive tests green.
- [ ] Keep all new visible strings in resources.
- [ ] Keep accessibility labels for new toggles/actions.

## Security / update path

- [ ] Keep package IDs stable.
- [ ] Keep Main and Helper signed by the permanent release certificate.
- [ ] Keep Helper control permission signature-protected.
- [ ] Verify downloaded APK package/version/hash/certificate before installer launch.
- [ ] Never weaken update verification for dev convenience.
- [ ] Verify upgrade and rollback paths without uninstalling.

## Performance / battery

- [ ] No permanent polling for features that can be event-driven.
- [ ] Bound all wake locks.
- [ ] Bound all sync/network waits.
- [ ] Avoid waking the process only for cosmetic state refresh.
- [ ] Review alarms/jobs for duplicate scheduling.
- [ ] Confirm diagnostics collection is on-demand or cheap.

# 9. Explicitly deferred / non-goals

## Mobile data

Public issue #6 was closed because normal third-party Android apps cannot reliably toggle mobile data without privileged `MODIFY_PHONE_STATE`/carrier privileges.

- Do not add root, Shizuku or ADB solely for mobile-data control.
- Revisit only if Android exposes a stable normal-app API in the future.

## Unsupported third-party internals

- Do not directly start/stop private services inside another app when the developer provides or is preparing a supported API.
- Do not mutate another app's persistent user configuration merely to simulate a temporary sleep state.

## Release scope

- Do not merge deferred feature or integration work into the current reliability candidate until the gate passes.
- Do not publish 0.7 as stable merely because CI is green; physical Thor regression and explicit acceptance are required.
