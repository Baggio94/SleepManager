# SleepManager 0.6.2 — implementation plan

> **Archived implementation record.** This plan documents the 0.6.2 refactor work that became the foundation of 0.7.0. Continue execution in [0.7.0](./0.7.0.md) and [0.7.0-validation](./0.7.0-validation.md).

This plan turns the private 0.6.2 roadmap into small, regression-controlled steps.

## Safety rules

1. One behavior-sensitive change at a time.
2. Do not stack the next behavior change until the current commit passes:
   - unit tests
   - Android lint
   - debug build
   - responsive/emulator regression suite when relevant
3. Preserve the stable 0.6.1 behavior unless a change is explicitly intended.
4. Refactors should first move code without changing behavior, then improve behavior in a separate commit.
5. Hardware-only behavior remains validated on the AYN Thor only when the change touches lid/dock/radios/power controls.

## Step 1 — Syncthing pre-sleep probe correctness

Status: **done — focused tests + private checks + responsive emulator regression green**

Verified issue:
- `SleepManagerService.applyFreshSleepActions()` calls `SyncthingConnector.sleep()`.
- `SyncthingConnector.sleep()` calls `SyncthingController.healthProbeRunning()`.
- That health probe performs local HTTP/HTTPS I/O.
- The sleep path is service/main-thread orchestration, so the probe must not run synchronously there.

Implementation goals:
- Move the pre-sleep Syncthing health probe to the existing background executor or another explicit worker.
- Keep STOP ordering deterministic.
- Preserve the existing STOP/FOLLOW ownership model.
- Represent probe results explicitly instead of silently treating an exception/unavailable probe as `false`.
- Add focused unit/behavior coverage before changing any other integration.

## Step 2 — Syncthing diagnostics truthfulness

Status: **done — private checks + responsive emulator regression green**

Verified issue:
- `buildSleepSummary(..., syncthing = AppPreferences.manageSyncthing(...))` currently emits `Syncthing paused` from the preference alone.

Implementation goals:
- Distinguish:
  - STOP sent
  - STOP confirmed
  - STOP not verified / state unavailable
  - STOP not sent
- Do not report `paused` or `resumed` unless the runtime result supports that wording.
- Keep Activity history concise and user-readable.

## Step 3 — Release pipeline safety

Status: **done — private Android checks, artifact reuse dry run and responsive/emulator regression green**

- Make stable publication depend on successful checks for the exact same commit.
- Prefer publishing APKs already produced by the validated pipeline.
- Keep private dev CI unsigned/debug unless release signing is explicitly required.
- Validate the release workflow without publishing a real stable release.

Implementation:
- `build.yml` remains the only stable APK compiler: tests, lint, signed release build, package/certificate checks, then immutable artifact upload.
- Stable publication also waits for the existing responsive/emulator suite on the same commit, called as a reusable workflow. Debug instrumentation builds remain separate from the signed release APKs.
- `publish-release.yml` is now called by that successful pipeline with the exact artifact ID. It downloads the APKs without Gradle, rebuilding or signing again.
- `scripts/release_artifacts.py` binds Main, Helper and `update.json` to the source commit, repository, variant, versions and SHA-256 hashes in `build-manifest.json`.
- Publication rejects prereleases, debug artifacts, mismatched commits/versions/hashes and a tag pointing to another commit.
- The build and stable publication are restricted to `Baggio94/SleepManager`. The private repository needs no signing secrets.
- Private checks exercise the same packaging/verification script with debug APKs, upload them, then download by artifact ID and verify them in a second job with read-only permissions.
- Existing published releases are left unchanged on reruns. New assets are uploaded into a draft before publishing. An existing draft fails explicitly and must be reviewed before retrying.
- Preview publication is unchanged; it is outside this stable-pipeline step.
