### Battery capacity sanity fallback — Issue #29

Public issue: [SleepManager #29 — Battery capacity shows wrong data](https://github.com/Baggio94/SleepManager/issues/29).

Observed on an AYN Thor Max at 80%:
- Android reports `capacity = 80`
- `charge_full = 8,336,000 µAh` while `charge_full_design = 5,938,000 µAh`
- `charge_counter = 6,674,635 µAh`, which is internally consistent with the incorrect learned `charge_full` because `6,674,635 / 8,336,000 ≈ 80%`

Conclusion for 0.6.2: SleepManager is not generating the ~8 Ah value; the device fuel gauge is exposing an implausible learned `charge_full`. SleepManager should nevertheless sanitize clearly impossible learned-capacity data before presenting it.

- [ ] Add a sanity check between `charge_full` and `charge_full_design` when both are available.
- [ ] Treat a learned `charge_full` that is clearly above design capacity as suspect; initial candidate threshold: `charge_full > charge_full_design × 1.25`, to be validated against real-device data/tests.
- [ ] When `charge_full` is plausible, preserve the current raw-value behavior.
- [ ] When `charge_full` is implausibly high, use `charge_full_design` as the displayed/full-capacity fallback rather than the learned value.
- [ ] In that fallback mode, sanity-check `charge_counter` too; if it is also physically inconsistent with the selected full capacity, derive displayed current capacity from `capacity% × selected full capacity` instead of showing the impossible raw counter.
- [ ] Keep the raw Android/fuel-gauge values available in diagnostics so firmware/calibration problems are not hidden by the UI fallback.
- [ ] Add focused tests for normal learned capacity, worn batteries below design capacity, implausibly high `charge_full`, implausible `charge_counter`, missing design/full/counter values, and percentage-derived fallback rounding.
- [ ] Retest the battery dashboard on the reporter's value pattern and on the physical AYN Thor before final 0.6.2 sign-off.

## Integrations

New integrations must use official, state-aware APIs. SleepManager should remember only the state it changed and restore only that state; do not modify another app's private preferences or force-stop it.

### Obtainium

Goal: temporarily suspend unnecessary background update work during sleep without changing the user's Obtainium schedule/settings.

Upstream status:
- [x] Request opened: [Obtainium #3355 — Temporary pause for background update work](https://github.com/ImranR98/Obtainium/issues/3355).
- [ ] Await upstream review / API support.

Preferred contract:
- temporary pause/resume that does not rewrite the user's configured update interval or enablement
- a readable current temporary-pause/background-work state
- already-running download/install/update work may finish safely
- queued WorkManager jobs honor the temporary pause before starting
- wake simply removes SleepManager's temporary hold; it does not need to force an immediate update check

SleepManager rules:
- [ ] do not modify Obtainium internal SharedPreferences directly
- [ ] do not force-stop Obtainium
- [ ] restore only a temporary pause owned by SleepManager

Related public SleepManager issue: #25.

### Key Mapper

Key Mapper already exposes:
- `ACTION_PAUSE_MAPPINGS`
- `ACTION_RESUME_MAPPINGS`
- `ACTION_TOGGLE_MAPPINGS`

Upstream status:
- [x] Request opened: [Key Mapper #2279 — Expose current mappings state through the Intent API](https://github.com/keymapperorg/KeyMapper/issues/2279).
- [x] Upstream agreed to add `ACTION_MAPPINGS_STATE_CHANGED` and emit it when the service starts, allowing a manifest receiver to establish the initial state and keep it cached.
- [ ] Wait for the upstream implementation/release before adding the SleepManager integration.

Planned SleepManager behavior:
- observe/cache the latest paused/active mappings state
- before sleep, pause only when mappings are active
- remember whether SleepManager performed that pause
- on wake, resume only when SleepManager owns the pause
- leave the Accessibility permission/service configuration intact

### RAOfflineProxy

Goal: stop the RetroAchievements offline proxy during sleep only when doing so will not interfere with its background cache queue, then restore only a proxy state changed by SleepManager.

Upstream status:
- [x] Request opened: [RAOfflineProxy #191 — External start/stop control API for automation apps](https://github.com/misantronic/RAOfflineProxy/issues/191).
- [x] Upstream proposed a state-aware `ProxyConfigProvider.call()` API with `start`, `stop` and `status`, idempotent UI-equivalent control, `notifyChange` state observation, a custom permission and queue information.
- [ ] Wait for the upstream implementation/release and validate Android 12+ foreground-service background-start behavior before enabling the integration.

Planned SleepManager behavior:
- read the provider status rather than controlling `ProxyService` directly
- if the cache queue is empty, stop an active proxy before sleep and restore it on wake only if SleepManager stopped it
- if cache work is queued/in progress, leave the proxy running by default; revisit user configurability only if needed
- use provider change notifications instead of polling
- never change RAOfflineProxy's autostart preference
